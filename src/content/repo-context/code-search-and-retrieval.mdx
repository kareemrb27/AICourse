Instruction files give the agent the rules. To make a change it also has to find the right code in a repository that may have millions of lines. This lesson compares the main ways agents do that.

## Four approaches

### 1. Agentic search with plain tools
The agent runs `grep`/`ripgrep`, lists directories and opens files, reasoning about what to look at next, the way a developer would. It needs no index, is always current, and works well when names are meaningful. It can be slow or wander in huge repos.

### 2. Embedding search (semantic retrieval)
Chunk the code, embed it, and fetch chunks similar to the task description. It helps when you do not know the right keyword ("where do we handle expired sessions?"). Costs: you must maintain an index, chunk boundaries can cut functions in half, and results can miss exact identifiers. Pair it with keyword search.

### 3. Repository maps
Build a compact outline of the codebase (files, classes and function signatures) and put the most relevant part in the prompt. Aider's repo map does this using **tree-sitter**, a parser that extracts definitions and references from source files, and ranks which symbols matter most for the current task within a token budget. The agent then knows what exists before opening anything.

### 4. Structural and code-graph search
Query the code's syntax or relationships instead of its text: "all callers of `charge()`", "classes that implement `Repository`". Tools like ast-grep search by syntax tree, and language servers provide go-to-definition and find-references.

## What research says

- **SWE-agent** argues that agents benefit from an interface designed for them: efficient search and navigation commands, compact editing and linting feedback. Its ablations found search and editing design mattered a great deal.
- **Agentless** proposes a deliberately simple pipeline of localizing the fault hierarchically (files, then classes and functions, then lines), generating a patch and validating it, without a long agent loop. It is a useful reminder that a clear localization step can compete with open-ended autonomy.
- **RepoCoder** studies repository-level completion by retrieving relevant code iteratively, using the model's own draft output to improve the next retrieval.

None of these settles the question in general. Benchmarks reflect their own tasks and tools, so test on your repo.

<Callout title="A practical default">
  Give the agent fast keyword search plus file reading first. Add a repo map for
  large codebases. Add embeddings or structural search only if you can show
  the simpler tools miss things you care about.
</Callout>

## Make your repo easy to search

- Use **descriptive names** for files and functions. They are the agent's primary search handle.
- Keep **directories organized** by feature or domain, with short README files in big folders.
- **Exclude noise** such as build output, vendored code and lockfiles from search with ignore files.
- Keep **tests near code** so the agent finds usage examples.
