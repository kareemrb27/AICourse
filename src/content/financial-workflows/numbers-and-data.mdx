Financial software has one non-negotiable rule: the numbers must be right. Language models are not calculators, and floating-point numbers are not money. This lesson covers both problems, and where trustworthy data comes from.

## Never use floats for money

Binary floating point cannot represent most decimal fractions exactly:

```python
>>> 0.1 + 0.2
0.30000000000000004
>>> from decimal import Decimal
>>> Decimal("0.1") + Decimal("0.2")
Decimal('0.3')
```

Use exact decimal types (Python's `decimal`, or integers of the smallest currency unit) end to end: parsing, storage, arithmetic and formatting. Pass money across APIs as strings or integers, never as JSON floats. Be explicit about **rounding mode** and where rounding happens, since rules differ by currency and context.

Also store the **currency** with every amount. A bare number is ambiguous. Keep the minor-unit exponent in mind, because it differs by currency (for example, some have zero decimal places and some have three).

## Do not let the model do arithmetic

Models can add small numbers and still fail on long ones, percentages across periods or unit conversions, and they fail with confidence. The pattern that works is to let the model **write down the calculation** and let code **run it**:

- **Program of Thoughts** prompting separates reasoning from computation by having the model express its reasoning as a program that an interpreter evaluates.
- **PAL** (Program-aided Language Models) likewise generates programs as intermediate steps and offloads the arithmetic to a runtime.
- **FinQA** is a dataset of numerical reasoning questions over financial reports, a good place to see what these questions look like.

In your system: give the model **calculation tools** (sum, percent change, currency conversion with a supplied rate, date difference) that take exact decimals and return exact decimals. Log every tool call so a reviewer can replay it.

## Get the facts from authoritative sources

Prefer structured, official data to text the model remembers or scrapes.

- **SEC EDGAR APIs** provide programmatic access to filing data for US public companies. Read the access rules and fair-use guidance, which include identifying your application.
- **XBRL** is the standard for tagging financial statement data in machine-readable form, so a figure can be retrieved by its tag instead of searched in prose.
- **FRED** (from the St. Louis Fed) offers an API for economic time series.
- **ISO 20022** is a messaging standard widely used for payments and financial messages, and a good model of structured financial data.

Cite the source and the retrieval date with every figure the system reports.

## Dates, periods and units

- Distinguish **fiscal year** from calendar year, and **period end** from filing date.
- Normalize **units** ("in thousands", "in millions") before comparing.
- Record **as-reported vs restated** values.
- Treat time zones and business-day calendars explicitly.

## Ledgers: how money records are kept

Accounting systems use **double entry**: every transaction posts equal debits and credits across accounts, so the books always balance and each movement has a counterpart. Martin Fowler's "Accounting Transaction" pattern describes the idea in software terms, and open-source tools such as Beancount show a plain-text ledger model.

Design implications for agents:

- Write to the ledger only through a **posting service** that enforces balance and validity.
- Make entries **append-only**. Fix mistakes with reversing entries, not edits.
- Link each posting to its source documents and approval record.

<Callout title="Cross-footing">
  Cheap, powerful check: recompute every total from the line items and compare
  to the stated total. Mismatches catch both model extraction errors and
  documents that are wrong.
</Callout>
