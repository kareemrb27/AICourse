A language model knows a lot about the world and nothing about your company. It has never read your policies, your tickets, your runbooks or last week's incident report. **Retrieval-augmented generation**, usually shortened to **RAG**, is the standard way to fix that: find the relevant passages in your own documents, hand them to the model with the question, and have it answer from them. It is the technique behind most "chat with your documents" products, and in this course you will build one yourself.

## The problem RAG solves

Models fall short on your documents in three ways:

- **They have not seen them.** Private and recent information is not in the training data.
- **They guess.** Asked about something they do not know, a model may produce a fluent, confident and wrong answer (a hallucination).
- **You cannot check them.** A plain answer comes with no source, so you cannot tell whether it is true.

RAG attacks all three. The model gets the right text at question time, is told to answer only from it, and can point to where each fact came from.

## The two phases

RAG has an **ingestion** phase you run once (and again when documents change), and a **query** phase that runs on every question:

```text

  documents -> clean text -> split into chunks -> turn each chunk into a vector -> store

QUERY (every question)
  question -> find the most relevant chunks -> build a prompt -> model answers -> show answer + sources
```

Each arrow is a place where things can go wrong, and the lessons ahead take them in order: preparing documents (lesson 2), searching (lessons 3 and 4), generating the answer (lesson 5) and measuring all of it (lesson 6).

The handbook is only about 1,800 words, which would fit into a single prompt with room to spare. We use it because it is small enough to read and to test, **not** because it needs RAG. Real document sets are thousands of times larger, and that is where RAG earns its place (see the decision table below).

Now a minimal pipeline. Retrieval here is crude on purpose: it counts the words a document shares with the question.

```python
import re

import anthropic

from handbook import DOCS

MODEL = "claude-opus-5-5"


def words(text):
    return set(re.findall(r"[a-z0-9]+", text.lower()))


def retrieve(question, docs, k=2):
    q = words(question)
    return sorted(docs, key=lambda d: -len(q & words(d["text"])))[:k]


def ask(client, question):
    sources = retrieve(question, DOCS)
    context = "\n\n".join(f"[{d['id']}] {d['title']}\n{d['text']}" for d in sources)
    response = client.messages.create(
        model=MODEL,
        max_tokens=2048,
        system=(
            "Answer using only the sources provided. If the sources do not contain the answer, "
            "say that you do not know. Cite the source id in square brackets after each fact."
        ),
        messages=[{"role": "user", "content": f"Sources:\n{context}\n\nQuestion: {question}"}],
    )
    answer = "".join(b.text for b in response.content if b.type == "text")
    return answer, [d["id"] for d in sources]


client = anthropic.Anthropic()
for question in ["How long does a VPN session last?", "When will my laptop be replaced?"]:
    answer, used = ask(client, question)
    print("Q:", question)
    print("sources used:", used)
    print("A:", answer, "\n")
```

That is a complete RAG system: retrieve, build a prompt from what was found, generate. Everything else in this course is about making each step **better and measurable**, because the version above has obvious problems. Its retrieval ignores meaning (a document about "approval" will not match a question about "permission"), it counts common words like "the" and "my", it returns whole documents instead of the relevant passage, and nothing checks the answer.

## RAG, long context or fine-tuning?

RAG is one of three ways to give a model knowledge, and the right choice depends on the situation:

| Approach | Best when | Watch out for |
| --- | --- | --- |
| **Put it all in the prompt** (long context) | The documents fit comfortably in the context window and change rarely | Cost and speed on every call (prompt caching helps), and answer quality can slip with very long inputs |
| **RAG** | The collection is large, changes often, or needs per-user access control, and answers need sources | More moving parts, and answers are only as good as retrieval |
| **Fine-tuning** | You need a consistent style, format or skill | It is poor at teaching facts reliably, and it is slow to update |
| **A search tool** (lesson 4 of the API course, applied) | The model should decide when and what to look up | More tool calls, and the model must search well |

A common mistake is to build RAG when the documents would simply fit in the prompt. A common opposite mistake is to stuff everything into the prompt when the collection has grown to millions of words. Do the arithmetic first: count the tokens in your documents, and compare the cost of sending them every time with the cost of retrieving a few chunks.

## What makes RAG succeed or fail

Most RAG problems are **search problems**. If the right passage is not retrieved, no model can answer correctly, and a stronger model just produces a more convincing wrong answer. So the discipline in this course is:

1. **Retrieve well**, and measure it separately from the answers.
2. **Instruct the model to stay inside the sources** and to say when they do not contain the answer.
3. **Show sources**, so a person can verify.
4. **Test with real questions**, including ones the documents cannot answer.

## Things to decide early

- **Which documents?** Who owns them, and are they current and consistent? RAG will faithfully repeat a wrong policy.
- **Who may see what?** If different people may read different documents, the access rules must be applied **before** retrieval, not after. A model that has seen a confidential passage can be coaxed into revealing it.
- **Where does the text go?** Chunks you retrieve are sent to the model provider with each question. Check that your data rules allow it. You can compute embeddings locally, as this course does, so the search step stays on your machine.
- **What does a wrong answer cost?** A chatbot that gets the cafeteria hours wrong is a nuisance. One that gets a refund policy or a medical instruction wrong is a liability, and needs human review.
